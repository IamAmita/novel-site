## 1. 設計方針

### 1.1 基本方針

- Django ORM（モデル）を中心に設計し、マイグレーションで DB を管理する
- テーブル名は `{app名}_{モデル名（小文字）}` の Django デフォルト命名規則に従う
- 全テーブルに `id`（BigAutoField）・`created_at`・`updated_at` を標準装備
- 論理削除が必要なテーブルには `deleted_at` カラムを設ける
- `master_*` テーブルは初期データをフィクスチャとして管理する

### 1.2 Django アプリとテーブルカテゴリの対応

| Django アプリ | テーブルカテゴリ | 主なテーブル |
|-------------|--------------|------------|
| `apps.users` | ユーザー系 | users, user_profiles, follows 等 |
| `apps.novels` | 作品系 | novels, episodes, sections 等 |
| `apps.worlds` | 世界系 | worlds, settings, setting_fields 等 |
| `apps.communications` | コミュニケーション系 | comments, evaluations, notifications 等 |
| `apps.common` | 汎用系 | categories, tags, templates |
| `apps.masters` | マスタ系 | master_statuses, master_classes 等 |
| `apps.administration` | 管理系 | reports, operation_histories, work_stats |

### 1.3 PostgreSQL 固有機能の活用

| 機能 | 用途 |
|------|------|
| `uuid-ossp` 拡張 | UUID 生成（将来的な公開 ID として活用） |
| `pg_trgm` 拡張 | 全文検索・あいまい検索の高速化 |
| `JSONB` 型 | `setting_fields` の柔軟なフィールド定義 |
| `GIN インデックス` | 全文検索・JSONB の高速検索 |

## 3. 主要テーブル詳細設計

### 3.1 users_user（ユーザー基本情報）

Django の `AbstractBaseUser` または `AbstractUser` を継承して実装。

| カラム名 | 型 | 制約 | 説明 |
|---------|---|------|------|
| `id` | BigInt | PK, Auto | ユーザーID |
| `username` | VARCHAR(20) | UNIQUE, NOT NULL | ユーザー名（3〜20文字、英数字・ハイフン） |
| `email` | VARCHAR(254) | UNIQUE, NOT NULL | メールアドレス |
| `password` | VARCHAR(128) | NOT NULL | ハッシュ化パスワード（bcrypt） |
| `is_active` | BOOLEAN | NOT NULL, DEFAULT TRUE | アカウント有効フラグ |
| `is_staff` | BOOLEAN | NOT NULL, DEFAULT FALSE | スタッフフラグ（Admin アクセス） |
| `email_verified_at` | TIMESTAMP | NULL | メール認証日時 |
| `created_at` | TIMESTAMP | NOT NULL | 作成日時 |
| `updated_at` | TIMESTAMP | NOT NULL | 更新日時 |
| `deleted_at` | TIMESTAMP | NULL | 論理削除日時 |

```python
# apps/users/models.py（イメージ）
class User(AbstractUser):
    username = models.CharField(max_length=20, unique=True)
    email = models.EmailField(unique=True)
    email_verified_at = models.DateTimeField(null=True, blank=True)
    deleted_at = models.DateTimeField(null=True, blank=True)
    created_at = models.DateTimeField(auto_now_add=True)
    updated_at = models.DateTimeField(auto_now=True)
```

## 6. マイグレーション方針

### 6.1 アプリ実装順序

マスタデータが他テーブルの外部キー参照元となるため、以下の順で実装する。

```
1. apps.masters     （外部キー参照元）
2. apps.common      （categories, tags）
3. apps.users       （ユーザー基本情報）
4. apps.novels      （作品系）
5. apps.worlds      （設定系）
6. apps.communications（コミュニケーション系）
7. apps.administration（管理系）
```

### 6.2 初期データ（フィクスチャ）

マスタ系テーブルは Django フィクスチャ（JSON 形式）で初期データを管理する。

### 6.3 論理削除の実装方針

`deleted_at` カラムを持つモデルにはカスタムマネージャーを実装し、通常クエリでは削除済みレコードを除外する。

```python
# 実装イメージ
class SoftDeleteManager(models.Manager):
    def get_queryset(self):
        return super().get_queryset().filter(deleted_at__isnull=True)

class Novel(models.Model):
    objects = SoftDeleteManager()
    all_objects = models.Manager()  # 削除済み含む全レコード用
    ...
```
