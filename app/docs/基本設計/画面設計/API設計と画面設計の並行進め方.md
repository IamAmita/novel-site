# API設計と画面設計の並行進め方

本ドキュメントは、API設計と画面設計を並行して進めるための具体的なアプローチを説明します。

---

## 1. 並行設計のメリット

### 1.1 早期の整合性確認
- **データの整合性**: 画面で必要なデータとAPIレスポンスの整合性を早期確認
- **操作フローの最適化**: 画面操作とAPI呼び出しタイミングの最適化
- **エラーハンドリングの統一**: 画面とAPIのエラー処理を統一

### 1.2 効率的な開発
- **設計の最適化**: 両方の設計を同時に最適化
- **変更の最小化**: 後からの大幅な変更を回避
- **開発速度の向上**: 並行作業による開発時間の短縮

## 2. 並行設計の進め方

### 2.1 共通基盤の整理

#### Step 1: データモデルの確認
```
1. DB設計の確認
   - エンティティ間の関係
   - 必須項目・オプション項目
   - データ型・制約

2. 画面で必要なデータ項目の洗い出し
   - 表示項目
   - 入力項目
   - 計算項目

3. APIで提供すべきデータの整理
   - レスポンス項目
   - リクエスト項目
   - 検索・フィルタ項目
```

#### Step 2: 操作フローの整理
```
1. ユーザー操作の洗い出し
   - 画面遷移
   - ボタンクリック
   - フォーム送信

2. API呼び出しタイミングの決定
   - ページ読み込み時
   - ユーザーアクション時
   - 定期的な更新

3. エラーハンドリングの設計
   - バリデーションエラー
   - ネットワークエラー
   - システムエラー
```

### 2.2 並行作業の具体例

#### 例：作品詳細画面の設計

**画面設計側**:
```
1. レイアウト設計
   - 作品情報表示エリア
   - 章一覧表示エリア
   - アクションボタン配置

2. 表示項目の整理
   - 作品タイトル
   - 作者名
   - 概要
   - タグ
   - 章一覧

3. 操作項目の整理
   - 編集ボタン
   - 章作成ボタン
   - いいねボタン
   - ブックマークボタン
```

**API設計側**:
```
1. エンドポイント設計
   - GET /api/v1/novels/{novel_id}
   - GET /api/v1/novels/{novel_id}/episodes
   - POST /api/v1/novels/{novel_id}/like
   - POST /api/v1/novels/{novel_id}/bookmark

2. レスポンス設計
   - 作品詳細情報
   - 章一覧情報
   - いいね・ブックマーク状態

3. エラーハンドリング
   - 作品が存在しない場合
   - 権限エラー
   - バリデーションエラー
```

**整合性確認**:
```
1. データ項目の整合性
   - 画面で表示する項目がAPIレスポンスに含まれているか
   - APIレスポンスの項目が画面で使用されているか

2. 操作フローの整合性
   - 画面の操作が適切なAPIを呼び出しているか
   - APIの呼び出しタイミングが適切か

3. エラーハンドリングの整合性
   - 画面のエラー表示がAPIエラーに対応しているか
   - エラーメッセージが統一されているか
```

## 3. 設計ツール・手法

### 3.1 設計ツール

#### 画面設計ツール
- **Figma**: ワイヤーフレーム・プロトタイプ作成
- **Adobe XD**: UI/UX設計
- **Sketch**: デザイン作成
- **InVision**: プロトタイプ・コラボレーション

#### API設計ツール
- **Swagger/OpenAPI**: API仕様書作成
- **Postman**: APIテスト・ドキュメント
- **Insomnia**: API設計・テスト
- **Stoplight**: API設計・ドキュメント

### 3.2 並行設計の手法

#### 1. プロトタイプ駆動設計
```
1. 画面プロトタイプの作成
2. APIモックの作成
3. プロトタイプとモックの連携テスト
4. 設計の調整・最適化
```

#### 2. ユーザーストーリー駆動設計
```
1. ユーザーストーリーの作成
2. 画面フローの設計
3. APIフローの設計
4. ストーリーの実現可能性確認
```

#### 3. データフロー駆動設計
```
1. データフローの整理
2. 画面でのデータ表示設計
3. APIでのデータ提供設計
4. データフローの最適化
```

## 4. 具体的な作業手順

### 4.1 フェーズ1（基本機能）の並行設計

#### Week 1-2: 基盤設計
```
画面設計:
- デザインシステムの定義
- 共通コンポーネントの設計
- 基本レイアウトの設計

API設計:
- 認証APIの設計
- ユーザー管理APIの設計
- 基本CRUD APIの設計
```

#### Week 3-4: 認証・ユーザー管理
```
画面設計:
- ログイン画面のワイヤーフレーム
- 新規登録画面のワイヤーフレーム
- プロフィール画面のワイヤーフレーム

API設計:
- 認証エンドポイントの詳細設計
- ユーザー管理エンドポイントの詳細設計
- エラーハンドリングの設計
```

#### Week 5-6: 作品管理
```
画面設計:
- 作品一覧画面のワイヤーフレーム
- 作品詳細画面のワイヤーフレーム
- 作品作成・編集画面のワイヤーフレーム

API設計:
- 作品管理エンドポイントの詳細設計
- 章管理エンドポイントの詳細設計
- 話管理エンドポイントの詳細設計
```

### 4.2 整合性確認のポイント

#### データ整合性
- [ ] 画面で表示する項目がAPIレスポンスに含まれている
- [ ] APIレスポンスの項目が画面で適切に使用されている
- [ ] データ型・形式が統一されている
- [ ] 必須項目・オプション項目が適切に設計されている

#### 操作整合性
- [ ] 画面の操作が適切なAPIを呼び出している
- [ ] APIの呼び出しタイミングが適切
- [ ] ローディング状態が適切に表示される
- [ ] エラー状態が適切に処理される

#### セキュリティ整合性
- [ ] 認証が必要な画面・APIが適切に保護されている
- [ ] 権限チェックが画面・API両方で実装されている
- [ ] 入力値のバリデーションが統一されている

## 5. 品質管理

### 5.1 設計レビュー
```
1. 画面設計レビュー
   - ユーザビリティの確認
   - デザインの一貫性確認
   - アクセシビリティの確認

2. API設計レビュー
   - RESTful設計の確認
   - セキュリティの確認
   - パフォーマンスの確認

3. 統合レビュー
   - 画面・APIの整合性確認
   - エンドツーエンドの動作確認
   - ユーザー体験の確認
```

### 5.2 テスト計画
```
1. 単体テスト
   - 画面コンポーネントのテスト
   - APIエンドポイントのテスト

2. 統合テスト
   - 画面・API連携のテスト
   - エンドツーエンドのテスト

3. ユーザビリティテスト
   - 実際のユーザーによる操作テスト
   - フィードバックの収集・反映
```
