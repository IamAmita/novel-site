## 【設計方針・運用ルールまとめ】

- 本DB設計は要件定義書・機能要件定義書をもとに、エンティティの洗い出し・分類・詳細化を段階的に進めている。
- エンティティは「ユーザー系」「作品系」「コミュニケーション系」「掲示板系」「管理・運用系」「その他」の6分類で整理。
- 各エンティティの詳細は分類ごとに個別ファイルで管理し、一覧は全体像把握・設計初期用。
- 主要な設計方針・運用ルール：
    - ユーザー情報とプロフィール情報は1対1で分離し、DBレベルでUNIQUE制約を付与。
    - フラグ（is_admin等）は初期のみ、将来的な権限拡張はuser_roles/rolesテーブルで柔軟に対応。
    - メールアドレス・ユーザー名はDBで一意制約。再利用不可が推奨。再利用時はサフィックス付与等で一意性維持。
    - 履歴・ログ系は「履歴種別」「操作ユーザーID」を持ち、定期アーカイブ・自動削除運用を推奨。
    - ダイレクトメッセージは送信者・受信者ごとに論理削除フラグを持ち、両者削除時のみ物理削除。
    - ブロック・通報は理由・解除日時・対応状況等を管理。
    - 2FA設定は方式・履歴を柔軟に管理できる設計を推奨。
    - コメントは共通テーブル方式（target_type, target_id）で管理。
- テーブルは細かく分けて拡張性・保守性を重視。ただしJOIN増加や運用煩雑化には注意。
- 設計方針・運用ルールは各分類ファイルにも適宜記載。

## ユーザー系
| エンティティ名         | 説明                                                         |
|------------------------|--------------------------------------------------------------|
| ユーザー情報           | 認証・管理に必要なユーザーの基本情報（ユーザー名、メールアドレス、誕生日等） |
| プロフィール情報       | 公開プロフィールや追加情報（画像、自己紹介、興味分野等）      |
| フォロー               | ユーザー同士のフォロー関係                                   |
| いいね                 | 作品や設定、コメント等への「いいね」情報                     |
| ダイレクトメッセージ   | ユーザー間の個別メッセージ                                   |
| 権限・ロール           | 作品や設定、掲示板などに対する権限管理                       |
| ユーザー情報系履歴     | ユーザー情報の変更・退会・停止等の履歴                       |
| 2FA設定                | 2段階認証の設定・履歴                                        |
| ログイン履歴           | ユーザーのログイン履歴                                       |
| ブロック               | ユーザー間のブロック関係                                     |
| 通報                   | 不適切ユーザーやコンテンツの通報情報                         |
