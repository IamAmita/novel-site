# ユーザー系エンティティ詳細

---

## 【設計メモ・方針まとめ】
- ユーザー情報とプロフィール情報は1対1で分離。
- ユーザー登録時に必ずプロフィールも同時作成、削除もセットで行う運用。
- is_admin等のフラグは初期のみ、将来的な権限拡張は権限管理テーブル・権限定義テーブルで柔軟に対応。
- 履歴・ログ系は「履歴種別」「操作ユーザーID」を持ち、定期アーカイブ・自動削除運用を推奨。
- ダイレクトメッセージは送信者・受信者ごとに論理削除フラグを持ち、両者削除時のみ物理削除。
- ブロック・通報は理由・解除日時・対応状況等を管理。

## 【ユーザー系エンティティ設計における主な考慮点】
- プロフィール情報の拡張性（将来的な複数プロフィールや公開/非公開対応など）
- 権限管理の粒度（どの対象にどの権限を付与できるかのルール整理）
- 退会・論理削除時のデータ保持方針（プロフィールや履歴の残し方、完全削除の有無）
- 2FAやセキュリティ設計（方式追加やbackup_codes運用は拡張時に見直し）
- 履歴・ログ系テーブルの肥大化対策（アーカイブ・自動削除運用ルールの設計）
- 外部サービス連携（SNSログイン等）を見据えた拡張性
- ユーザー状態管理（BAN、凍結、一時停止などの多様な状態管理）

## ユーザー情報エンティティ属性一覧

| 属性名             | 型         | 必須 | 一意 | 説明                         |
|--------------------|------------|------|------|------------------------------|
| id                 | int        | ○    | ○    | ユーザーID（主キー）         |
| account_name       | varchar    | ○    | ○    | アカウント名（自分で定める一意の識別名） |
| email              | varchar    | ○    | ○    | メールアドレス               |
| password_hash      | varchar    | ○    |      | パスワード（ハッシュ化）     |
| birthdate          | date       | ○    |      | 生年月日                     |
| is_active          | tinyint    | ○    |      | 有効/停止フラグ（0:停止、1:有効） |
| delete_flg         | tinyint    | ○    |      | 論理削除フラグ（0:有効、1:削除） |
| deleted_at         | datetime   |      |      | 論理削除日時                 |
| two_factor_enabled | tinyint    | ○    |      | 2段階認証有効フラグ（0:無効、1:有効） |
| created_at         | datetime   | ○    |      | 登録日時                     |
| updated_at         | datetime   |      |      | 更新日時                     |
| last_login         | datetime   |      |      | 最終ログイン日時             |

### ユーザー情報エンティティ設計補足
- アカウント名（account_name）はユーザーが自分で定める一意の識別名。DBで一意制約を付与し、原則として再利用不可・変更は厳格な運用とする。
- delete_flg（論理削除フラグ）とdeleted_at（削除日時）で退会・削除状態を管理し、物理削除は原則行わない。復活時はこれらの値をリセットする。
- 退会時は物理削除せず、is_active（有効/無効フラグ）やdeleted_at（退会日時）で「退会状態」を管理し、アカウント名・メールアドレス等の一意情報は保持する。他ユーザーが同じ情報で新規登録できないようにする。
- 退会後90日間は復活可能とし、その間はデータを保持。復活時は登録済みメールアドレスへの認証リンク送信などで本人確認を行い、再有効化できる。90日経過後は完全削除も選択肢とする。
- メールアドレスはDBで一意制約。再利用不可が推奨。再利用時はサフィックス付与等で一意性維持。
- メールアドレスの変更履歴は履歴テーブルで管理。
- パスワードはPBKDF2+ソルト+ストレッチングでハッシュ化し、詳細はセキュリティ設計書参照。
- 生年月日は閲覧権限に関係するためユーザー情報側で管理。
- 有効/停止フラグ（is_active）は0/1で管理（0:停止、1:有効）。退会・停止理由や日時は履歴テーブルで管理。
- 2段階認証有効フラグ（two_factor_enabled）は0/1で管理（0:無効、1:有効）。詳細は2FA設定テーブルで管理。
- 最終ログイン日時の詳細な履歴はログイン履歴テーブルで管理。

## 履歴・ログ系テーブル設計補足
- 履歴・ログ系テーブルはデータ量が増えやすいため、アーカイブや自動削除の運用ルールを設計段階で決めておく。
