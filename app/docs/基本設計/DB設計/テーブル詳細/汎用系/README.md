# 汎用系テーブル詳細

---

## 概要
汎用系テーブルは、複数のエンティティで共通して使用される汎用的な機能を管理するテーブル群です。

---

## 設計方針
- 汎用性を重視し、複数のエンティティで再利用可能な設計
- マスターデータによる柔軟な拡張性
- 履歴管理と論理削除によるデータの完全性確保
- パフォーマンスを考慮したインデックス設計

---

## テーブル一覧

### 分類・タグ系
- [categories.md](./categories.md) - カテゴリ管理テーブル
- [tags.md](./tags.md) - タグ管理テーブル

## ステータス管理の分割設計

### 背景
従来の統合型`statuses`テーブルから、エンティティ別の専用ステータステーブルに分割しました。

### 分割の理由
1. **シンプルさ**: 各テーブルの目的が明確
2. **パフォーマンス**: エンティティ固有の最適化が可能
3. **保守性**: エンティティごとの仕様変更が容易
4. **拡張性**: エンティティ固有のステータス追加が容易

### 分割後のテーブル構成

#### ユーザー系
- [user_statuses.md](../ユーザー系/user_statuses.md) - ユーザーステータス管理
  - アカウント状態（通常、警告中、一時停止、永久停止）
  - 通報数による自動ステータス変更
  - 管理者による手動ステータス変更

#### 作品系
- [setting_statuses.md](../作品系/setting_statuses.md) - 設定ステータス管理
  - 完成度（下書き、作成中、完成、アーカイブ）
  - 年齢制限（全年齢、R-15、R-18）
  - 公開状態（非公開、公開、限定公開）

#### コミュニケーション系
- [notification_statuses.md](../コミュニケーション系/notification_statuses.md) - 通知ステータス管理
  - 重要度（未読、既読、重要、緊急）
  - 複合ステータス管理
  - フィルタリング機能

---

## 共通設計パターン

### ステータス管理の共通要素
- **履歴管理**: ステータス変更の履歴を保持
- **論理削除**: データの完全性を保ちながら履歴を保持
- **マスタ参照**: master_statusesによるステータス定義の一元管理
- **変更理由**: ステータス変更の理由を記録
- **複合一意制約**: 重複設定の防止

### インデックス設計
- 主キー（id）
- 複合一意制約（エンティティID + ステータスID）
- 現在のステータス検索用（エンティティID + created_at）
- ステータス検索用（status_id）
- 変更日時検索用（created_at）
- 削除フラグ検索用（is_deleted）

### 制約条件
- 外部キー制約による参照整合性
- チェック制約による値の範囲制限
- ユニーク制約による重複防止

---

## 移行時の注意点

### データ移行
1. 既存の統合テーブルから各専用テーブルへのデータ移行
2. 重複データの確認と除去
3. 外部キー制約の確認

### アプリケーション修正
1. ステータス取得ロジックの変更
2. クエリの最適化
3. インデックスの調整

### 段階的移行
1. 既存テーブルとの並行運用期間の設定
2. 段階的な機能移行
3. 動作確認とロールバック計画

---

## 運用上の注意点

1. **マスタデータ管理**: master_statusesの適切な管理
2. **パフォーマンス監視**: 各テーブルのパフォーマンス監視
3. **データ整合性**: 定期的なデータ整合性チェック
4. **バックアップ**: 各テーブルの適切なバックアップ
5. **監査ログ**: ステータス変更の監査ログ管理
