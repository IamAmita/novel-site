# users テーブル詳細

---

## 概要
ユーザーの基本情報を管理するテーブルです。認証情報、アカウント状態、セキュリティ設定などを含みます。

---

## テーブル定義

| 属性名             | 型         | 必須 | 一意 | 説明                         |
|--------------------|------------|------|------|------------------------------|
| id                 | int        | ○    | ○    | ユーザーID（主キー）                 |
| account_name       | varchar    | ○    | ○    | アカウント名（自分で定める一意の識別名） |
| email              | varchar    | ○    | ○    | メールアドレス                       |
| password_hash      | varchar    | ○    |      | パスワード（ハッシュ化）             |
| birthdate          | date       | ○    |      | 生年月日                             |
| reported_count     | int        | ○    |      | 被通報回数                           |
| is_active          | tinyint    | ○    |      | 有効/停止フラグ（0:停止、1:有効）    |
| delete_flg         | tinyint    | ○    |      | 論理削除フラグ（0:有効、1:削除）     |
| deleted_at         | datetime   |      |      | 論理削除日時                         |
| two_factor_enabled | tinyint    | ○    |      | 2段階認証有効フラグ（0:無効、1:有効） |
| created_at         | datetime   | ○    |      | 登録日時                             |
| updated_at         | datetime   |      |      | 更新日時                             |
| last_login         | datetime   |      |      | 最終ログイン日時                     |

---

## インデックス

| インデックス名 | 種類 | 説明 | カラム |
|----------------|------|------|--------|
| PRIMARY KEY | 主キー | ユーザーIDの主キー | id |
| UNIQUE | 一意 | アカウント名の一意制約 | account_name |
| UNIQUE | 一意 | メールアドレスの一意制約 | email |
| INDEX | 通常 | 被通報回数検索用 | reported_count |
| INDEX | 通常 | 有効ユーザー検索用 | is_active |
| INDEX | 通常 | 論理削除フラグ検索用 | delete_flg |
| INDEX | 通常 | 登録日時検索用 | created_at |

---

## 制約条件

### 主キー制約
- `id`: 自動採番（AUTO_INCREMENT）

### 一意制約
- `account_name`: アカウント名は一意である必要があります
- `email`: メールアドレスは一意である必要があります

### チェック制約
- `birthdate`: 現在日付以前である必要があります
- `is_active`: 0または1の値のみ許可
- `delete_flg`: 0または1の値のみ許可
- `two_factor_enabled`: 0または1の値のみ許可

---

## 設計補足

### アカウント名（account_name）
- ユーザーが自分で定める一意の識別名
- DBで一意制約を付与し、原則として再利用不可・変更は厳格な運用とする
- 変更時は履歴テーブルに記録

### 論理削除
- `delete_flg`（論理削除フラグ）と`deleted_at`（削除日時）で退会・削除状態を管理
- 物理削除は原則行わない。復活時はこれらの値をリセットする
- 退会時は物理削除せず、`is_active`（有効/無効フラグ）や`deleted_at`（退会日時）で「退会状態」を管理
- アカウント名・メールアドレス等の一意情報は保持し、他ユーザーが同じ情報で新規登録できないようにする
- 退会後90日間は復活可能とし、その間はデータを保持

### メールアドレス
- DBで一意制約。再利用不可が推奨
- 再利用時はサフィックス付与等で一意性維持
- メールアドレスの変更履歴は履歴テーブルで管理

### パスワード
- PBKDF2+ソルト+ストレッチングでハッシュ化
- 詳細はセキュリティ設計書参照

### 生年月日
- 閲覧権限に関係するためユーザー情報側で管理

### 有効/停止フラグ（is_active）
- 0/1で管理（0:停止、1:有効）
- 退会・停止理由や日時は履歴テーブルで管理

### 2段階認証有効フラグ（two_factor_enabled）
- 0/1で管理（0:無効、1:有効）
- 詳細は2FA設定テーブルで管理

### 最終ログイン日時
- 詳細な履歴はログイン履歴テーブルで管理

### 被通報回数（reported_count）
- ユーザーが投稿したコメント等を通報された回数
- バッチ処理で通報数を集計・更新
- 一定数（例：20回）で自動的にステータス変更
- ステータス変更は`user_statuses`テーブルで管理

---

## 関連テーブル

- `user_statuses`: 1対多の関係（ユーザーのステータス管理）
- `user_profiles`: 1対1の関係（ユーザープロフィール情報）
- `two_factor_auth`: 1対多の関係（2段階認証設定）
- `login_histories`: 1対多の関係（ログイン履歴）
- `user_permissions`: 1対多の関係（ユーザー権限管理）
- `user_histories`: 1対多の関係（ユーザー情報変更履歴）

---

## 運用上の注意点

1. **アカウント名変更**: 厳格な運用が必要。履歴テーブルに記録
2. **メールアドレス変更**: 本人確認が必要。履歴テーブルに記録
3. **論理削除**: 90日間の復活期間を設ける
4. **パスワード**: 定期的な更新推奨
5. **2FA**: セキュリティ向上のため推奨
6. **ステータス管理**: 被通報回数に応じた自動ステータス変更（user_statusesテーブルで管理）
7. **通報処理**: バッチ処理で被通報回数を集計・更新
